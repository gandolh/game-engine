# audit-29 — Nothing verifies the committed wasm binaries match their AssemblyScript source

status: todo
created: 2026-09-13
context: repo audit 2026-09-13 (`improve`). The project's own README names this exact risk and nothing mitigates it.

## The gap

Committing the wasm artifacts is deliberate and correct — CLAUDE.md and
[decisions.md](../../wiki/decisions.md) both state a fresh clone must not need to build wasm first, and the
binaries live under `games/farm/client/public/wasm/` plus `engine/wasm-modules/dist/`.

What is missing is any check that the committed binary was rebuilt after a source edit. No test, no git
hook (verified: only stock `.sample` hooks), no CI (see [audit-06](2026-09-13-audit-06-ci-gate.md)).

`engine/wasm-modules/README.md` states the risk in its own words: **"stale committed `.wasm` is a silent
correctness bug."**

## Failure scenario

A contributor fixes a bug in [engine/wasm-modules/src/pathfinding.ts](../../../engine/wasm-modules/src/pathfinding.ts)
and forgets `npm run build-wasm`. The only test touching the wasm output,
[engine/core/src/wasm/pathfinder.test.ts](../../../engine/core/src/wasm/pathfinder.test.ts), loads the
**existing** `dist/pathfinding.wasm` bytes and asserts against them — it has no way to know the source
changed, so it stays green while the shipped binary still contains the bug.

The blast radius is every game using the kernel, plus both servers (the Farm server reads wasm from
`engine/wasm-modules/dist/` specifically to match what the browser runs), plus the determinism baseline —
which is captured with `PATHFINDER=wasm` precisely because JS and WASM are not route-equivalent
([audit-21](2026-09-13-audit-21-pathfinder-equivalence-test.md)). A stale binary therefore corrupts the
baseline silently.

## Fix sketch

A cheap drift check, in rough order of preference:

1. **Hash manifest.** Commit a manifest of source hashes alongside the artifacts; a test recomputes the
   hashes of `src/*.ts` and fails if they differ from the manifest. Fast, no toolchain needed at test time,
   and works in CI and locally. Downside: the manifest must be regenerated by `build-wasm` (make that
   automatic in `build/compile.mjs`).
2. **Rebuild-and-compare in CI.** Run `asc` and byte-compare against the committed binaries. Most direct,
   but requires `asc` output to be deterministic — **verify that before relying on it**; if the compiler
   embeds timestamps or paths, byte-comparison will produce false failures and option 1 is the right answer.

Whichever is chosen, it must also cover the **two** artifact locations (`engine/wasm-modules/dist/` and
`games/farm/client/public/wasm/`), which can themselves drift from each other — check whether they are
currently in sync as part of this work and report it.

## Files you OWN
- [engine/wasm-modules/build/compile.mjs](../../../engine/wasm-modules/build/compile.mjs) (emit the manifest)
- new test in `engine/wasm-modules/` or `engine/core/src/wasm/`
- `engine/wasm-modules/package.json` — a `test` script if the test lands there (see
  [audit-20](2026-09-13-audit-20-tool-workspaces-test-scripts.md))
- a note in `engine/wasm-modules/README.md` describing the guard

## Files you must NOT touch
- the AssemblyScript sources
- the committed binaries themselves — **do not rebuild and commit new artifacts as part of this spec.** If
  the check reveals the committed binaries are *already* stale, stop and report that as its own finding; it
  is a correctness issue needing its own verification, not a drive-by commit.

## Acceptance
- Editing a `src/*.ts` kernel without rebuilding makes `npm run test` **fail** with a clear message naming
  the stale artifact. Demonstrate it, then revert.
- A clean tree passes.
- Whether the two artifact locations are currently in sync is stated explicitly.
- If option 2 was chosen, the determinism of `asc` output is demonstrated, not assumed.
